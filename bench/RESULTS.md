# Python vs Rust on the Dipulse BMS protocol path

This is the measurement that motivated `py2rs`: the same pure-Python protocol
code, converted to Rust by the transpiler, running on the same inputs.

## What was converted

`py2rs` transpiled three modules of the Dipulse gateway's RS-485 stack, with
**zero diagnostics**:

| Python module | Lines | What it is |
|---|---:|---|
| `gateway/app/drivers/bms/jk/frames.py` | 363 | Frame builders, CRC-16, Modbus RTU response parsing |
| `gateway/app/drivers/bms/jk/parser.py` | 261 | JK proprietary TLV parser → `JKTelemetry` |
| `gateway/app/drivers/bms/models.py` | 103 | `BMSTelemetry` dataclass, `TelemetryState` enum |

These modules are the gateway's per-poll decode path. Every BMS poll decodes
frames through them, so they run on every cycle for every pack.

## Method

1. `bench/make_fixtures.py` builds the fixture set **from the original Python
   code**, so both sides measure identical bytes. It synthesises three frame
   families — Modbus RTU FC 0x03 read responses, JK proprietary TLV
   responses, and JK PB-Series 308-byte frames — using the project's own CRC
   routine.
2. `bench/bench_python.py` runs the workloads against the **unmodified**
   Dipulse modules.
3. The Rust side runs the **transpiled** modules, generated by `py2rs`.
4. Each workload computes an FNV-1a 64-bit digest of its results. The digests
   are compared before any timing is read: identical digests prove the two
   implementations compute the same answers.

No write frames are built and no serial hardware is touched — this is a
decode-path benchmark only.

## Results

Best of 9 runs, 4096 frames per family (8192 Modbus frames: 16-cell block +
40-word summary block), CPython 3.13.16 vs Rust 1.99.1 `--release`.

Three consecutive invocations of `run_bench.ps1` were made; the table gives
the median run and the range observed across all three. The machine was not
CPU-pinned, so the Python figures vary by roughly ±10%.

| Workload | Frames | Python (µs/frame) | Rust (µs/frame) | Speed-up | Observed range | Parity |
|---|---:|---:|---:|---:|---:|---|
| Modbus RTU FC 0x03 response parse | 8192 | 77.51 | 1.02 | **70–81×** | 66–81× | MATCH |
| JK proprietary TLV parse | 4096 | 32.34 | 0.85 | **31–40×** | 31–40× | MATCH |
| JK PB-Series frame validation | 4096 | 1489.42 | 6.62 | **198–230×** | 198–230× | MATCH |

Total for one full poll cycle of all 16 384 frames: **6.87 s in Python,
43.9 ms in Rust** — a 156× reduction in decode time.

Digests (identical on both sides, for every run):

```

```

## Why the PB-Series path gains the most

`_crc16_modbus` is a bit-at-a-time CRC-16:

```python
crc = 0xFFFF
for byte in data:
    crc ^= byte
    for _ in range(8):
        if crc & 0x0001:
            crc = (crc >> 1) ^ 0xA001
        else:
            crc >>= 1
```

That is 8 Python-level iterations per byte. The PB-Series path runs it twice
over 306 bytes — 4 896 interpreted loop iterations per frame. The transpiled
version is the same algorithm in Rust, and the compiler unrolls the inner
loop's bounds checks away; it is ~80× faster.

The Modbus path gains less because it is already mostly C-level work
(`struct.unpack`, slicing), so a larger share of the Python cost is in the
*call* overhead rather than in the loop body — which is exactly the overhead
Rust removes.

## Reproducing

```powershell
.\bench\run_bench.ps1 -Repeat 9 -Count 4096
```

This transpiles, builds the generated Rust, regenerates the fixtures, runs
both sides and prints the comparison table above.

Individual steps:

```powershell
.\py2rs\run.ps1 build --root .\Dipulse `
    --entry gateway/app/drivers/bms/jk/parser.py --out .\rust_out
cd bench; python make_fixtures.py --count 4096
python bench_python.py --repeat 9
..\rust_out\target\release\dipulse_protocol.exe fixtures.bin 9
```

## Parser coverage

`py2rs scan --root .\Dipulse` parses **226 of the 237** Python files in the
Dipulse repository. All 11 failures are `async def` — the one construct the
parser deliberately does not accept. The transpiler then needs far more than
parsing: it has to type the code and lower it faithfully, which it does for
the protocol layer.

## Caveats

- The Rust figures are for the transpiled modules in isolation, not for a
  whole gateway process. In production the surrounding I/O (serial reads,
  SQLite writes, the FastAPI layer) would dominate, and the protocol decode
  would be a small slice of it.
- The benchmark measures decode only. It says nothing about start-up cost,
  binary size, or the effort of keeping the Rust and Python versions in sync.
- `py2rs` currently transpiles the protocol layer only. The driver, transport,
  command-queue and API layers rely on asyncio, threads and dataclass
  machinery that the compiler does not model yet.
